## 3. 我提出的要求，以及它们在项目里落到了哪

| 我的要求 | 项目里的体现 |
|---|---|
| 这是作业，不是研究项目，不做性能测试，不做技术选型对比 | 没有 benchmark；评估只做验收用例；检索直接选 BM25，没有和向量检索做对比实验 |
| 先保证基础功能分，再扩展工程复杂度 | C01–C09 先覆盖题目 6 个必须验收点和步数上限；之后才加 C10–C20 的业务场景，以及录制回放、内容哈希、故障注入 |
| 关注业务逻辑细节，比如用户说了某句特定的话时 Agent 该怎么办 | 设计草案第 5 节 9 个难点；对应用例 C11（"别管冲突直接给个数"）、C14（"听说改成 60 天了"）、C16（文档里混入指令）、C17（"那个怎么申请"） |
| 难点写成"具体样例 + 每种做法的好坏 + 判断时注意什么"，关注真实对话里难判断的地方 | 设计草案第 5 节的格式 |
| 全文用初学者能看懂的话，精简 | 所有文档 |
| 复用我已有的 LLM API | DeepSeek，OpenAI 兼容协议，配置见 `.env.example` |

## 4. 我拍板的 6 个业务口径

设计草案第 12 节列出了 6 个需要业务方决定的问题，每个都附了默认方案。我审阅后全部采用默认方案。它们在实现里的位置：

| 口径 | 决定 | 落在哪 | 验证用例 |
|---|---|---|---|
| 文档写明适用范围时怎么答 | 分情况作答，不请求确认 | 提示词规则 4c | C02（差旅按 D03）、C13 |
| 法律常识类问题 | 判资料外，不用模型常识回答 | 提示词规则 5；核验规则 6 | C19 |
| 部分可答 | ANSWERED + gaps，不单设 PARTIAL | 提示词规则 7 | C15 |
| 引用是否支持回答 | 不做模型评判，只做整句扩展 | `gate.py` 的 `locate_sentence` | 单元测试 |
| 步数上限 | 8 次模型调用 | `.env` 的 `KBQA_MAX_STEPS` | C09 |
| 交付方式 | 只做 CLI，不做 HTTP API | `src/kbqa/cli.py` | README |

口径 2 在第一次录制时暴露了一个缺口：提示词只写了"不用法律知识回答"，没写"资料里有相关公司规定时状态怎么定"，结果 C19 被标成 ANSWERED。按我定的口径，补了一条通用规则后重录（03 第 5 节）。

## 5. AI 生成内容是怎么验证的

| 验证 | 结果 | 位置 |
|---|---|---|
| 单元测试 + 脚本 Mock 流程测试 | 39 个通过 | `tests/` |
| 真实 DeepSeek 跑 20 个用例并录制 | 第一次 18/20，修改后第二次 20/20 | `examples/eval_report.md`、`examples/history/run1/` |
| 回放复现 | 20 个用例回放结果和录制结果逐字一致 | `tests/test_replay.py` |
| 逐条读 20 个用例的实际回答 | 发现 5 处断言抓不到的问题，已列出、没有隐藏 | 03 第 6 节 |

开发中发现并修正的 AI 错误（AI 自己写的东西出了问题）：

| 问题 | 怎么发现的 | 怎么处理 |
|---|---|---|
| 核验规则 5 留了出口，把模型从"请求确认"推成了"直接回答"（C08） | 读第一次录制的 Trace | 加核验规则 7，重录 |
| 注入测试实际没测到东西，含注入文本的文档检索不到（C16） | 读 Trace，发现模型从没读过 D09 | 改文档标题，重录 |
| 关键段落 D01§3 在检索里只排第 5 | 开工时试检索 | 加段落标题权重 |
| 只命中一个泛词也被判为 good（"那个怎么申请"） | 开工时试检索 | 加最低分数门槛 |
| 一次回放按旧逻辑重写了 examples 下的报告和 Trace | 运行后检查报告头 | 改 CLI 让回放不写文件；报告头如实说明 |
