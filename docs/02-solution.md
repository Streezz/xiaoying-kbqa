# 02 方案：调用流程、动态决策、技术取舍

## 1. 一句话

模型自己决定"搜什么、读哪段、要不要查版本、什么时候结束"；程序只负责执行工具，并在模型想结束时用证据账本把关。

## 2. 架构

```
 问题 + 会话ID
      │
      ▼
   CLI ◄──────► 会话库 SQLite（历史问答 + 证据账本）
      │
      ▼
 ┌──────────────── Agent 循环（最多 8 次模型调用）────────────────┐
 │                                                                  │
 │  DeepSeek ──选工具──► 工具层 ──结果──► 观察 ──► DeepSeek 下一步   │
 │     │                  ├ search_docs   BM25 + 同义词              │
 │     │                  ├ read_section  读原文 ──► 记入证据账本    │
 │     │                  └ get_doc_info  版本 / 生效 / 范围 / 替代  │
 │     │                                                            │
 │     └─想结束─► submit_result ─► 结束前核验 ─不过关─► 退回原因 ──┘
 │                                    │
 └────────────────────────────────────┼──────────────────────────────
                                      ▼
                            结构化结果 + Trace（jsonl / md）
```

| 文件 | 干什么 |
|---|---|
| `src/kbqa/agent.py` | 循环：调模型、执行工具、拼观察、计步数、到上限停 |
| `src/kbqa/tools.py` | 4 个工具的说明、参数校验、执行、判重 |
| `src/kbqa/gate.py` | 结束前核验 |
| `src/kbqa/ledger.py` | 证据账本 |
| `src/kbqa/docstore.py` | 读文档、切段、算哈希、算"今天"的状态 |
| `src/kbqa/retriever.py` | BM25 + 同义词归一 + hit_quality |
| `src/kbqa/llm.py` | DeepSeek、录制回放、两种 Mock |
| `src/kbqa/prompts.py` | 系统提示词、每轮的对话背景 |
| `src/kbqa/session.py` | SQLite 会话 |
| `src/kbqa/trace.py` | 运行记录 |
| `src/kbqa/faults.py` | 故障注入 |
| `src/kbqa/evaluate.py` | 跑用例、断言、写报告 |

## 3. 一次提问怎么走

1. 读会话：历史问答和证据账本。账本里内容已变化的段落（哈希对不上）先作废。
2. 发给模型：系统提示词 + 对话背景（上一轮的问题、状态、回答、引用原文、冲突、向用户提的问题）+ 本轮问题。
3. 模型返回一个或多个工具调用，每个都带一句 `reason`。
4. 程序执行，把结果压成 JSON 发回。
5. 重复 3、4，直到模型调用 `submit_result`。
6. 核验通过就结束；不通过，把问题列表发回，模型继续（算一步）。
7. 第 8 次模型调用后还没通过，返回 INCOMPLETE，附上已读过的段落（标明未经核验）。

## 4. 动态决策落在哪

骨架固定，但下面这些全由模型根据工具结果决定，程序不写 if：

| 工具结果 | 模型可能的下一步 | 用例 |
|---|---|---|
| hit_quality = good，只有一份相关 | 读原文 → 提交 ANSWERED | C01 |
| hit_quality = weak / none | 换书面用语再搜 → 还是没有就 NO_EVIDENCE | C03、C04、C19 |
| 多份文档数字不同 | 读双方原文 → get_doc_info → 按版本 / 生效日期 / 范围判断，判断不了就请求确认 | C02、C13 |
| get_doc_info 显示待生效 | 按现行版回答，说明将来的变化 | C05 |
| get_doc_info 显示废止 | 标为不适用 | C02 |
| 工具返回 TIMEOUT / NOT_FOUND | 换参数重试、读另一段，或者提交 FAILED | C06、C07、C08 |
| 核验退回 | 按原因补读原文、补表态、补查证，或改状态 | 见各 Trace |
| 上一轮是 NEED_CONFIRMATION，本轮用户选了一份 | 按用户确认的制度回答 | C10 |
| 上一轮读过的段落内容变了 | 重新读，改结论 | C20 |

## 5. 核心机制：证据账本 + 结束前核验

账本记下本会话 `read_section` 读到的每段原文和它的哈希；`get_doc_info` 查过的文档也记下。
模型调用 `submit_result` 时，`gate.py` 检查：

1. 引用必须读过：只在搜索预览里出现过的不算。
2. 原文一字不差：quote 去掉空白后必须是原文的子串。通过后把 quote 扩展成整句返回给用户。
   如果被截掉的部分有"原则上、特殊情况、批准、仅、除"这类词，退回一次，提醒模型可能漏了例外条件（难点 9）。
3. 原文没变：账本里的哈希必须等于当前文件的哈希。
4. 读过的都要表态：本轮读过的、被引用的文档都要在 doc_verdicts 里写 basis / conflict / not_applicable。
   已废止的不能当 basis 或 conflict；待生效的不能当 basis。
5. 冲突要查证：冲突双方都要读过原文，都要查过 get_doc_info。
6. 状态和字段对得上：ANSWERED 要有 basis 引用；NEED_CONFIRMATION 要有冲突和确认问题；NO_EVIDENCE 不能有"数字+单位"的具体规定；FAILED 必须本轮真有工具失败。
7. 没读到的不能装作读到：本轮有文档读取失败、之后也没成功读到，就不允许 ANSWERED，也不能靠把它标成 not_applicable 绕过去，只能 FAILED。
   这条是第一次录制后加的，原因见 03 的 C08。

为什么要这一层：提示词只能"要求"模型，核验是"检查"。没有它，模型偶尔一次拿搜索预览当依据、或读到冲突文档却只引一份，结果里看不出来。
有了它，这两类关键缺陷要么被退回修正，要么以 INCOMPLETE 结束，不会以 ANSWERED 的样子出去。

核验管不到的：引用是真的但回答意思理解错了（比如把"30 天"说成"一个月"之外的意思）。这部分没有做语义判断，见 03 的限制。

## 6. 工程措施

| 措施 | 做法 | 位置 |
|---|---|---|
| 步数上限 | 每轮最多 8 次模型调用（核验退回也算），到上限 INCOMPLETE | `agent.py` / `.env` |
| 工具调用上限 | 每轮最多 15 次，超了返回 TOOL_LIMIT 让模型用已有结果提交 | `agent.py` |
| 重复调用拦截 | 同参数第 2 次返回缓存并提示，第 3 次不执行 | `tools.py` |
| 统一返回格式 | `{ok, data, error_code, error_msg}`，参数错返回 BAD_ARGS 不抛异常 | `tools.py` |
| 基础设施重试 | 工具超时、模型网络错误各重试 1 次，不算模型决策 | `tools.py` / `llm.py` |
| 故障注入 | `--fault search:timeout@1,2`、`read:not_found@D02` 等 | `faults.py` |
| 内容哈希 | 每段原文算哈希，文档变了旧证据作废 | `docstore.py` / `ledger.py` |
| 多套资料 | `--data data/variants/xxx` 一键换 | `data/variants/` |
| 录制回放 | 按请求内容哈希存取模型响应；回放缺录像直接报错，不偷偷联网 | `llm.py` |
| 离线 Mock | 规则 Mock（CLI 用）和脚本 Mock（测试用），都明确标注只验证流程 | `llm.py` |
| Trace | 每个动作一行 JSON，结束后补"下一步"，另出 Markdown 表 | `trace.py` |
| 会话 | SQLite 两张表：轮次、账本 | `session.py` |
| 固定"今天" | `KBQA_TODAY`，判断生效的日期不依赖机器时钟 | `.env` |

## 7. 技术选型

| 选了什么 | 版本 | 承担的职责 | 为什么 |
|---|---|---|---|
| 原生 Python 循环 | Python 3.13 | Agent 循环 | 循环本身 100 多行；核验要插在"模型想结束"和"真结束"之间，自己写最直接 |
| DeepSeek `deepseek-chat` | API，OpenAI 兼容 | 决策：选工具、写回答 | 支持 function calling 和并行工具调用；aii 下其他项目已在用 |
| openai SDK | 3.40.0 | 发请求、解析 tool_calls | 只用 `chat.completions.create` |
| 自己实现 BM25 + jieba | jieba 0.42.1 | 检索 | 资料十几份，BM25 够用；结果确定，测试稳定 |
| PyYAML | 6.0.3 | 文档元数据、同义词表 | |
| pydantic | 2.14.1 | 工具参数校验 | 只是实现细节 |
| SQLite | 标准库 | 会话 | 不用装数据库 |
| typer | 0.27.3 | CLI | |
| pytest | 9.2.0 | 测试 | |

没用 LangGraph / ADK / AgentScope 等框架。

没做向量检索：资料少，同义词表 + 模型改写已经覆盖用例里的口语问法；
而且向量检索里"15 天"和"30 天"很接近，反而更难区分冲突。写进了 05 的下一步。

## 9. 和设计草案的差异

`设计草案.md` 是开工前写的，实现时改了这些：

- 用例从 10 个扩到 20 个，编号重排（C01 改成产品 FAQ，最简单的一条路径）。
- `d02_scoped` 原计划写"仅适用于差旅"，但 D03 已经管差旅且是 10 日，会造成新的冲突，改成"仅适用于驻外分支机构"。
- D01 总则加了"差旅另有规定的从其规定"，让"范围必须能引用"这条规则有原文可引。
- 工具调用上限从 12 调到 15：第一次试跑 C02，模型并行读了 6 段 + 查信息，用了 11 次。
- 检索加了段落标题权重和最低分数门槛：不加时 D01§3 在"报销期限"下只排第 5；"那个怎么申请"只命中一个泛词却被判为 good。
- 增加 `d02_updated` 变体和 C20，演示会话中途文档被更新。
- 第一次录制后改了三处（详见 03 第 3 节）：核验加第 7 条（C08）；提示词规则 5 补"资料里有相关公司规定时也用 NO_EVIDENCE"（C19）；
  注入文档 D09 改成和报销相关的标题，原来那份根本检索不到，C16 的"通过"不算数。
